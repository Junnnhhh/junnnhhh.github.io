## 🔥 Kafka란?
#### Kafka의 등장 배경
🔖기존 시스템들은 보통 아래처럼 동작
```
서비스 A → 서비스 B → 서비스 C 
```
##### 이 구조의 문제 점
- 서비스끼리 강하게 연결됨 (Tight Coupling)
- 특정 서비스 장애 시, 전체 영향
- 트래픽 증가 시, 병목 발생
- 데이터 흐름 추적 어려움

##### 특히, 대규모 서비스에서는 아래와 같은 작업이 폭증하기 시작
- 로그 수집
- 실시간 데이터 처리
- 이벤트 전달
- 사용자 행동 분석

**그래서 나온 개념이**
```
"중간에서 데이터를 안전하게 계속 흘러보내자"
```

👉 이걸 해결하기 위해 나온 대표 기술이 `Kafka`
➕ Kafka는 원래 LinkedIn 에서 대용량 로그 처리용으로 개발됐고, 현재는 Apache Kafka로 오픈소스화 됨.
___

#### 메시지 큐와 이벤트 스트리밍
##### 메시지 큐(Message Queue)
👉 메시지를 중간 저장소에 넣고, 필요한 시스템이 가져가는 방식.
```
Producer → Queue → Consumer
```
**대표 특징**
- 비동기 처리
- 서비스 분리 가능
- 장애 전파 감소

___
#### 이벤트 스트리밍(Event Streaming)
Kafka는 단순 Queue보다 더 발전된 개념.
Kafka는 데이터를
```
"흘러가는 이벤트(Event)의 흐름"
```
으로 관리.

**예시**
- 회원 가입 이벤트
- 주문 생성 이벤트
- 결제 완료 이벤트
- 로그 이벤트

이런 이벤트들을 실시간으로 계속 저장하고 전달함.

👉 즉, Kafka는
```
메시지 큐 + 실시간 데이터 스트리밍 플랫폼
```
___
#### Kafka를 사용하는 이유?
##### 1️⃣ 대용량 처리
👉 엄청난 양의 데이터를 빠르게 처리 가능

**예시**
- 로그 수집
- 실시간 주문 처리
- 채팅 시스템
- 사용자 행동 분석

##### 2️⃣ 서비스 간 결합도 감소
기존
```
A → B 직접 호출
```
Kafka 사용
```
A → Kafka ← B
```
서로 직접 몰라도 됨.

##### 3️⃣ 징에 잔피 빙지
👉 Consumer가 죽어도 Kafka에 데이터 남아있음. (나중에 다시 읽기 가능)

##### 4️⃣ 실시간 처리 가능
👉 이벤트를 거으 실시간으로 전달 가능

___
#### Kafka의 주요 특징
##### 1️⃣ 고가용성(High Availability)
👉 Broker 여러 대로 클러스터 구성 가능, 일부 서버 죽어도 서비스 지속 가능.

##### 2️⃣ 확장성(Scalability)
👉 서버(Broker) 추가로 성능 확장 가능, 수평 확장에 매우 강함.

##### 3️⃣ 내구성(Durability)
👉 디스크 기반 저장, 메모리가 아니라 파일로 저장해서 안정적.

##### 4️⃣ 대용량 처리
👉 초당 수십~수백만 건 처리 가능, Kafka의 가장 큰 강점 중 하나.

___

#### Kafka 사용 사례
##### 📖 로그 수집
```
Application → Kafka → ELK
```

##### 📖 실시간 알림
```
주문 발생 → Kafka → 알림 서버
```

##### 📖 데이터 파이프라인
```
DB → Kafka → Hadoop/Spark
```

##### 📖 마이크로서비스 이벤트 전달
```
결제 서비스 → Kafka → 배송 서비스
```

